### Deviations from the plan

- **N-4 hashes the committed files, not the working tree.** The first version hashed the working tree, and `test_redteam_v02.py::test_verify_never_runs_prepare_for_a_refused_dependency_source` caught the problem. In manual mode the agent edits the working tree, so its `[tool.uv]` change made `verify` exit 6 (untrusted surface) instead of 3 (dependency violation). That asked the user to trust the agent's change, and no violation was recorded. `HEAD` is what a clone or pull brings. ADR-0032 records this. The trust path reads git objects only and checks the command policy first, so a refused argv still exits 6 even when `git` is not on PATH (`test_trust_cli.py::test_a_path_link_to_a_hard_denied_program_is_refused`).
- **N-1 classifies more than 5xx and 429 as "no answer":** any status other than found or gone, and an unreadable answer. A retry would hit the same proxy, so failing the attempt would spend budget on retries that cannot pass. "No tagged version" and "no release time" are answers about the module; they fail the attempt.
- **The session 2 tests live in a second module** (see above).
- **The package cache also sets a per-attempt `GOCACHE`** for gates and prepare. Gates had no writable Go build cache under `srt` (Part 2 observation E). It is per attempt, so nothing is shared.
- **`state` cannot import `execution`** (import-linter), so the git reads for N-4 live in `execution/git.py` (`list_tree`, `committed_head`), the pure pinning in `state/trust_store.py` (`select_toolchain`, `pin_toolchain`), and the glue in `app/trust.repository_surface`, which `doctor` now uses too.

### Open items from the session 2 review (not fixed; for the owner)

1. **The integration branch's toolchain files versus HEAD's** (low). The surface pins `HEAD`, but a build runs on `aipm/integration`. When that branch has diverged (only a warning), its older `.cargo/config.toml` may never have been shown. Option: at build start, refuse (exit 6) when `pin_toolchain` of the integration head differs from HEAD's.
2. **More files that change where code comes from** (low): the files `yarnPath` and Yarn `plugins` point to (`.yarn/releases/*.cjs`), mise's own configs (`mise.toml`, `.mise.toml`, `.config/mise.toml`), `package.json#packageManager` (corepack), `.nvmrc` and `.node-version`. Hash them, or list them in ADR-0032 as not hashed.
3. **More `pass_env` names** (low; your list): `GOPATH`, `PKG_CONFIG`, `COREPACK_*`, `AR`, `TARGET_CC`, `HOST_CC`, `CC_<target>`, `CFLAGS`, `LDFLAGS`, `RUBYGEMS_GEMDEPS`, `BUNDLE_*`, `GEM_HOME`, `GEM_PATH`, `GRADLE_USER_HOME`, `MAVEN_OPTS`, `GRADLE_OPTS`.
4. **Without `srt`, the run cache's Cargo settings are not watched** (info). `~/.cargo/config.toml` is in the build watch, but the run's `CARGO_HOME` is not. Option: hash `protected_cache_paths()` before and after each attempt.
5. **The `registry_unavailable` report** (info). It leaves out the minor post-change violations and any definite findings from the same lookup, and a build does not save the gate report.
6. **An agent that commits a toolchain change in manual mode** (info). `verify` then refuses at trust before the checks run, and the post-change checks still catch the change after the user re-trusts. Option: name the commits since the snapshot that changed toolchain files in the "untrusted" error.
7. **A local `replace` gets around the lookup before prepare** (medium, re-review; not verified with a real Go toolchain). The agent adds `replace golang.org/x/text => ./ign/text` (a module already required at a cached version) and writes `ign/.gitignore` (`*`) and `ign/text/go.mod` at `go 1.16` requiring `attacker.example/m v1.0.0-<hex>`. The ignored directory is not in the change set (R-11), so no new name or version appears; `go mod download` reads the replacement's unpruned graph, and the proxy fetches the version from its origin. It needs `allow_new_dependencies: allow` or an approved `deps_add` to leak through an attacker's module. Options:
   - (a) Hold prepare when a changed `go.mod` adds or changes a local `replace` whose target `go.mod` is neither tracked at the base nor in the change set.
   - (b) Before prepare, read every local-replace target's `go.mod` from disk and look up its requirements too. This costs lookups for every monorepo that uses local replaces.

   Also treat lowering the `go` line below 1.17 as a dependency change.
8. **pnpm may hard-link from the store after all** (low, unverified). pnpm 10 may let a committed `pnpm-workspace.yaml` (`packageImportMethod: hardlink`) override the environment, and `pnpm-workspace.yaml` is not in the surface. Options: `--package-import-method=clone-or-copy` in the `node-pnpm` prepare argv (a template and trust change), and hashing `pnpm-workspace.yaml`. Check this under the real pnpm in the `srt` CI job.
9. **Smaller items from the re-review** (low or info):
   - On Linux, `remove_tree`'s last fallback, a by-name `chmod` of an unreadable directory, races a leftover process. Fixed in session 5, item 3.
   - `verify` creates its cache before taking the lock, with a run ID that has 16 random bits per minute, so a collision with a running build would empty the build's cache (about 1/65536).
   - A very deep tree makes `rmtree` slow at the end of a run.
   - `FileTrustStore.surface_hash()` hashes the surface without the toolchain files; only tests call it. Rename or remove it.

### Item 3: the cache cleanup's check-then-chmod race

| Commit | What changed |
|---|---|
| `2932315` | `_make_writable` no longer changes a directory by name. Tests: `test_v04_d3_3_cleanup_race.py`. |
| `0e3c272` | CHANGELOG, this section. |
| `a8569af` | Re-review fixes: a cache root the cleanup cannot open is left instead of raising; the tests swap after the EACCES too, skip as root, and stop tracking a closed descriptor; this section's counts. |

`remove_tree` makes each directory 0700 before emptying it. Before, `_make_writable` tried a no-follow `fchmodat`, then an `O_RDONLY | O_DIRECTORY | O_NOFOLLOW` descriptor, and for a directory it could not read, `lstat` followed by `chmod` by name, following links. Now:

1. Open the directory `O_RDONLY | O_DIRECTORY | O_NOFOLLOW` and `fchmod` the descriptor (every system). An error from `fchmod` (macOS `chflags uchg`) no longer escapes `remove_tree`.
2. On EACCES only, on Linux: open it `O_PATH | O_NOFOLLOW | O_DIRECTORY`, check `S_ISDIR(fstat)`, and `chmod /proc/self/fd/<fd>`. A link or a file swapped in is refused by `O_DIRECTORY`; a swap after the open changes only the directory that was opened. Without `/proc`, nothing is changed.
3. On EACCES only, without `O_PATH` (macOS): the no-follow `fchmodat`, which changes a link itself, never its target. Where it fails, nothing is changed.

A directory none of these reach is left under the cache root by `rmtree(ignore_errors=True)`. For the root itself, `os.fwalk` raises when it cannot open it; `remove_tree` suppresses that, so the root is left too.

**Deviation from the prompt:** the prompt kept the no-follow `fchmodat` as the first try. The review found that it changes a **hard link** to an outside file swapped in for the directory (it is not a link to follow), on macOS and on glibc 2.41. So the descriptor comes first, and `fchmodat` is only the macOS fallback after EACCES.

Checked by hand in Docker (`python:3.13-slim` and `python:3.14-slim`: Python 3.13.18 and 3.14.10, glibc 2.41, uid 1000; and the repository's tests in `ghcr.io/astral-sh/uv:0.13.6-python3.13-trixie`). ubuntu-latest's glibc 2.39 was not checked by hand; the Ubuntu "Checks" jobs run the same tests.

- The no-follow `fchmodat` (`os.chmod(..., follow_symlinks=False)`) **works** for a real directory, also a mode-0000 one, with and without `dir_fd`. It fails only for a link: `ValueError` with `dir_fd`, `NotImplementedError` without. So `_make_writable`'s old comment ("Linux refuses the pair") was wrong for glibc 2.32 and later, and on ubuntu-latest the old by-name step ran only for links (where `lstat` stopped it). glibc's implementation itself falls back to `/proc` when the kernel lacks `fchmodat2`.
- `os.fchmod` on an `O_PATH` descriptor fails with EBADF; `chmod /proc/self/fd/<fd>` works on it. `O_PATH | O_NOFOLLOW | O_DIRECTORY` on a link fails with ENOTDIR.
