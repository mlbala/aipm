## 1. Scope

Everything v0.2 adds on top of v0.1: `aipm verify`, `aipm scan` and `aipm task`; the gate runner and the command gates; the built-in gates `secrets`, `sast`, `deps`, `ac_trace` and `ac_review`; the scanner wrappers and the registry lookups; the `srt` sandbox profiles; the hardened git wrapper, the attempt snapshot and the `.pm/` write ledger (ADR-0021); the post-change checks; the LLM response cache; the Claude subagents and skills; the stack templates `python-pip`, `node-npm` and `node-pnpm`; and `install.sh`. The v0.1 surface was attacked again where v0.2 changed it (`aipm prompt` now runs git on the work tree).

The attacker controls any combination of `idea.md`, every file in the target repository (including a cloned repo's `.pm/`, and the `.git/` directory of a repository copied whole), every LLM response, agent output and diffs, test and scanner output, and registry metadata. The attacker does not control the user's terminal input, the user-level config (including the global git config) or aipm's installed code.

Agent dispatch, worktrees, `build`, `merge`, the scheduler and budgets across tasks arrive in v0.3; they are out of scope here except where noted.

`srt`, gitleaks, semgrep, osv-scanner and trivy were not installed on the test machine. The sandbox and scanner paths were attacked through the code and the stub binaries in `tests/fakes/bin/`; the one test that needs the real `srt` (`test_the_gate_network_profile_blocks_outbound_connections`) was skipped.

## 2. Attack surface

### 2.1 Where T2 data enters (new in v0.2)

| Entry | Read by | Becomes |
|---|---|---|
| The work tree after the agent ran: every changed, untracked and ignored file | `execution/git.py` (`change_set`), `security/diff_checks.py` | the change set, the post-change checks, scanner input, the AC reviewer's diff, the commit |
| `.git/config`, `config.worktree`, included files, a submodule's config, `.gitattributes`, `.git/info/*` | git itself, on every call `execution/git.py` makes | which programs git runs, what it lists, what it stages |
| Manifests and lockfiles (`pyproject.toml`, requirements files, `package.json`, `uv.lock`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `pylock.toml`) and package-manager settings (`.npmrc`, `.pnpmfile.cjs`, `uv.toml`) | `security/diff_checks.py`, `gates/builtin/deps.py`, the prepare step | dependency violations, registry lookups, what prepare installs |
| Test reports at `{report_file}` | `gates/reports.py` | the unit gate's verdict, `ac_trace` |
| Gate and scanner output, scanner JSON reports | `gates/command_gate.py`, `scanners/*` | gate results, findings, run artifacts, `prompt --fix` |
| Registry metadata (PyPI simple API, npm documents) | `scanners/registry.py` | the existence and age verdicts |
| The AC reviewer's reply, and cached replies in `.pm/cache/llm/` | `roles/ac_reviewer.py`, `llm/cache.py` | the veto, injection signals |
| Processes the gates start, including children that outlive them | the work tree, the attempt's temp dir | anything aipm reads after the gates |

### 2.2 Where aipm executes, writes, prints or decides (new in v0.2)

- **Executes:** git (`status`, `diff`, `ls-files`, `read-tree`, `ls-tree`, `cat-file`, `hash-object`, `config`, `add`, `commit`) outside any sandbox; the prepare step and command gates under `srt` (or unsandboxed with a warning); the scanners on a staged copy; `srt`'s interpreter; config-defined scanners for `aipm scan`.
- **Writes:** `.pm/runs/`, `.pm/cache/llm/`, the attempt snapshots and ledger in the user state directory, the attempt's temp dir (srt settings, reports, staged copies), the user's git index and branch (`verify --commit`), `.claude/agents/` and `.claude/skills/` (sync-context).
- **Prints:** gate summaries and last lines, scanner findings, the reviewer's evidence, task details.
- **Decides:** severe or minor per violation, whether prepare runs, each gate's verdict, `done`, the commit, what the AC reviewer is shown.

### 2.3 Compared with SECURITY.md §13.1

Two threats were missing and are added:

- **T-8**: a repository copied with its `.git` directory makes aipm's git calls run a program (RT02-1). v0.1 ran only `git rev-parse`, so the v0.1 pass rightly found the `-c` options enough; v0.2 runs `diff`, `status` and `commit`.
- **T-9**: a dependency enters through a source or a lockfile entry nobody approved (RT02-2, RT02-3). E-4 covered typosquats of declared names only.

I-5 gained a sharper example (a credential file in the AC reviewer's diff, RT02-5), and D-3 (orphaned processes) a new consequence: a gate's child that leaves its process group survives on macOS and can change the tree before `verify --commit` stages it (RT02-8, residual risk R-14).

## 3. Attacks tried

Result: **Bypassed** means the attack worked before this pass and is now fixed (section 4). **Held** means the existing controls stopped it. **By design**, **Residual** and **Not reachable** are explained in the row.

### I-1: no process starts with an argv outside the trusted menu or fixed fragments

| 2 | A config hook (`hook.<name>.command`, git 2.5x) for `post-index-change`, `prepare-commit-msg`, `post-commit`, `reference-transaction`: `core.hooksPath=/dev/null` and `--no-verify` do not stop it; it ran during `read-tree` and `verify --commit` (C-039) | **Bypassed**, RT02-1 |

The re-review also listed setups the fixes now refuse on purpose, each with a hint: a team-shared `[include] path = ../.gitconfig` (copy the settings into `.git/config`), an old-style submodule, a repository-level `hook.<name>.command`, more than 64 included config files, `-e .` in a requirements file, and every new `-r` or `-c` line.

## 5. Fuzzing

`tests/property/test_redteam_v02_props.py` adds ten properties (`485abf6`; its commit message says eleven). `uv run pytest tests/property --hypothesis-profile=ci-long` runs each at least 2,000 times; all v0.1 and v0.2 properties pass.

| Target | Property |
|---|---|
| Git config syntax | Every include path git itself reads from a generated config (any case, header-line settings, quotes, comments, continuations) is one the integrity snapshot watches; git is the oracle |
| Lockfile sources | A lockfile entry passes as registry only when its URL's scheme is `https` and its host is exactly `registry.npmjs.org` or `registry.yarnpkg.com` (userinfo, look-alike suffixes, ports and backslashes generated) |
| Requirement lines | A line read as a package name holds no URL, no `@` before its markers, no path and no archive |
| Deny list | Every path the repo map withholds from an LLM, the AC reviewer withholds too |
| Test reports | Any bytes parse to a report or are refused with `ReportError`, never another exception |
| Gate output | Saved output holds no ESC, C1 CSI or BEL, and no registered fake secret, however escapes split it |
| Claude subagents and skills | Hostile fields give files that pass I-3, or are refused |
| Attempt snapshot and ledger | Damaged JSON is refused (exit 6), never read as another task's snapshot |
| Post-change checks | Random manifests and lockfiles never crash the checks, the result is deterministic, and every newly added `evil.example` source is flagged |
| Stack templates | No argv the four stack templates accept holds a hard-denied program |

The `ci-long` runs found two things the default 100 examples did not. First, a requirement such as `requests~/` was read as the name `requests`; pip refuses that line, so it was not exploitable, but the version syntax is now strict. Second, after the review's fixes, `requests>=2.whl` was still read as a name, while pip reads any requirement ending in an archive extension as a local file: now the text before the markers must not end like an archive. Both count as sources outside the registry. Two oracles were too broad at first (they put one format's text into another format's file name) and were corrected.

## 6. Residual risks and open decisions

SECURITY.md §15 gains two entries and one changes:

- **R-13**: the prepare step runs repository code (a build backend, `setup.py`, a `.pnpmfile.cjs` the repository already had) and may write the user's package caches, which other projects read outside any sandbox. A malicious repository, or one whose build files an earlier task changed, could poison a cached wheel or a pnpm store file. That is a design property of SECURITY.md §9.1 (prepare may write the package-manager cache), so this pass proposes a change rather than making one: give prepare a private cache per attempt (`UV_CACHE_DIR`, `PIP_CACHE_DIR`, `npm_config_cache`, pnpm's `store-dir`), at the cost of downloads on every verify.
- **R-14**: a gate's child that starts its own session leaves the gate's process group, and on macOS nothing kills it (no process namespace). It keeps write access to the work tree. RT02-8 makes `verify --commit` notice what it changes before the commit; after verify returns, nothing does. v0.3 runs gates in a worktree that is removed afterwards.
- **R-11** now also names a wholly new directory whose own `.gitignore` ignores everything.

For the owner to decide (the definition of done of build prompt 09):

- **O-1 (low): `--ignore-pnpmfile` in the `node-pnpm` template.** A `.pnpmfile.cjs` an agent writes is caught (RT02-4), but one the repository already has runs during prepare. Adding the flag changes the prepare argv, which `tests/unit/test_config.py::test_v02_templates_pass_the_policy` pins exactly, so it needs the owner's decision.
- **O-2 (medium): R-13, a private package cache for prepare.** As above.
- **O-3 (info): config hooks on git 2.54.** Config hooks arrived in git 2.54, and it was not confirmed whether 2.54 already honours the event-level `hook.<event>.enabled` that aipm sets; tested on 2.55. On 2.54 a hook in the user's own global config may run during `verify --commit` (a repository's hooks are refused on every version). Options: require git 2.55 when `git hook` exists, or accept.

The v0.1 open items O-1 to O-4 are unchanged: none was decided in step 06.

## 7. Recommendations for v0.3

1. **Decide O-1 and O-2** before dispatch, where prepare runs after an agent that is otherwise sandboxed.
2. **Commit from verified bytes.** RT02-8 detects a swapped file after the commit. In worktrees, build the commit from the objects hashed before the gates (`hash-object -w`, a temporary index, `commit-tree`) so nothing can be swapped in at all.
3. **Kill what a gate leaves behind.** Run gates in a worktree that is removed after each attempt, and on Linux rely on `srt`'s PID namespace; on macOS, check for processes with the worktree as their working directory before reusing it.
4. **Back `done` with a local record** (v0.1 recommendation 2): `build` and `merge` will act on `done`, so a cloned `tasks.yaml` must not be enough.
5. **Attack the new surfaces first:** the adapter argv and `--resume`, `AIPM-BLOCKED`, context-file poisoning that survives `sync-context`, the scheduler's ownership overlap with worktrees, budget checks under `--parallel`, and the integration branch.
6. **Run the real tools in CI** for the red-team suite: `srt` (the network test is skipped without it), gitleaks, semgrep and osv-scanner, so the scanner wrappers are tested against the versions they claim to support.
7. **Run `ci-long` nightly** (v0.1 recommendation 6, still open).
